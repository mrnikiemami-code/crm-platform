# برنامهٔ اجرایی استقلال برند و ارتباطات CRM

تاریخ: ۱۸ اکتبر ۲۰۲۶ — ۲۶ مهر ۱۴۰۵  
مبنای بررسی: `acb99294fe49f29d90a4064eef9546a7842f4bbf` از `origin/crm-platform`  
وضعیت: برنامه مصوب برای اجرای کرسر؛ BI-01 آمادهٔ اجراست. هیچ پیاده‌سازی یا استقرار جدیدی توسط این commit انجام نشده است.

## هدف قابل تحویل

نسخه‌ای با برند شما که در صفحه‌ها، آیکون نصب، ایمیل‌ها، لینک‌ها، راهنما و بستهٔ نصب، کاربر را به Twenty هدایت نکند و از مرورگر، API، worker، نصب و به‌روزرسانی هیچ ارتباطی با زیرساخت آن تولید نکند. قابلیت‌های فعلی CRM، ویرایش و ساخت الگو، preview، احراز هویت، مجوز کاربر و ارسال پیام باید حفظ شوند.

تمرکز این برنامه فنی است. پیاده‌سازی لایسنس محصول پروژهٔ جداگانه است تا با تغییر برند و شبکه مخلوط نشود. هیچ screenshot به‌عنوان خروجی یا شرط قبولی لازم نیست.

## مرحلهٔ ۱ — Help کاملاً داخلی، همراه با موجودی نقاط برند

**اولویت اجرایی جدید:** اولین تحویل اجرایی، راهنمای داخلیِ قابل استفاده است. تسک دقیق: [BI-01 — Internal Help](../tasks/BI-01-internal-help.md). نام و لوگوی نهایی مانع این تسک نیستند.

**کار:** Help و Documentation و جست‌وجوی راهنما از سایت‌ها و موتورهای خارجی قطع شوند. route داخلی، محتوای واقعی فارسی، جست‌وجوی محلی، لینک‌های هم‌مبدأ و جلوگیری از راه‌اندازی support chat خارجی پیاده شوند. مسیرهای برنامه‌ساخته در ایمیل و dashboard و metadata نیز بررسی شوند.

**موجودی موازی در همان محدوده:** مصرف‌کنندگان Help و نقاط باقی‌ماندهٔ برند، فایل، شرط اجرا و معیار قبولی مشخص داشته باشند. قرارداد برند مشترک برای مرحلهٔ ظاهر تعریف شود؛ ساخت abstraction بدون مصرف یا تغییر غیرضروری بسته‌ها مجاز نیست.

**خروجی قابل بررسی:** کاربر Help را می‌زند، راهنمای داخلی دارای مقاله و جست‌وجو می‌بیند؛ هیچ Help خارجی باز یا فراخوانی نمی‌شود. جزئیات محتوا و معیارهای A–J در فایل تسک است.

**مرز:** این تحویل، اثبات قطع تمام ارتباط‌های محصول نیست؛ telemetry، icons، marketplace و بقیهٔ مراحل جدا می‌مانند.

## مرحلهٔ ۲ — تمام سطوح ظاهری و دارایی‌ها

**کار:** عنوان تب، ورود/ثبت‌نام، onboarding، sidebar، loading، صفحه‌های خطا، command menu، تنظیمات، admin، نمایش اپ‌ها، tooltip/alt/aria، راهنمای متنی و ترجمه‌های قابل عرضه بازبینی شوند. لوگوها و illustrationهای برنددار، favicon، manifest، آیکون‌های iOS/Android/Windows و تصویر اجتماعی از assetهای محلی ساخته شوند.

**پوشش:** تم روشن و تیره، فارسی RTL و زبان‌های واقعاً عرضه‌شده، workspace تازه و قدیمی، کاربر بدون آواتار، workspace بدون لوگو و صفحات قبل از ورود. عنوان‌های پویا علاوه بر HTML اولیه بررسی شوند. لوگوی اختصاصی مشتری بدون اجازه بازنویسی نشود.

**خروجی:** همهٔ صفحه‌ها و اپ نصب‌شونده برند شما را نشان دهند؛ بارگذاری تصویر و فونت برای برند از منابع محلی باشد.

**شما چه چیزی چک می‌کنید؟** ورود، sidebar، تنظیمات، تب مرورگر و نصب اپ روی دسکتاپ/موبایل را باز می‌کنید؛ هیچ نام یا نشان تبلیغاتی Twenty و هیچ تصویر خراب دیده نشود. با لوگوی workspace خالی هم نتیجه درست بماند.

## مرحلهٔ ۳ — همهٔ لینک‌ها، شبکه‌های اجتماعی و ایمیل‌ها

**کار:** Community، X، Discord، GitHub، معرفی شرکا، changelog، docs، help، سایت، پشتیبانی، تماس و صفحه‌های footer به مقصد خودتان یا صفحهٔ محلی منتقل شوند. مسیر غیرضروری که جایگزین ندارد حذف شود. همین کار در subject، preview text، body، logo، footer و لینک اقدام تمام ایمیل‌های دعوت، تأیید ایمیل، بازیابی/تغییر رمز و اعلان مدیریت انجام شود.

**ایمنی:** لینک ورود یا بازیابی از origin معتبر همین نصب ساخته شود، نه Host header دلخواه یا مقصدی از درخواست کاربر. token و زمان انقضای آن حفظ شوند. تصاویر ایمیل روی سرویس خود شما با URL قابل دسترسی گیرنده یا روش embedding آزموده‌شده ارائه شوند؛ `localhost` داخل ایمیل ارسال‌شده قابل قبول نیست. سیاست نصب آفلاین و ایمیل داخلی جدا بررسی شود.

**خروجی:** کلیک روی هر لینک محصول، کاربر را به مقصد خودتان می‌برد؛ ایمیل سیستمی هم برند و دامنهٔ شما را دارد.

**شما چه چیزی چک می‌کنید؟** یک دعوت و یک بازیابی رمز در mailbox آزمایشی می‌بینید؛ عنوان، تصویر، footer و دکمهٔ اقدام درست‌اند و token روی همین نصب کار می‌کند. هیچ ایمیلی به مخاطب واقعی برای آزمون ارسال نشود.

## مرحلهٔ ۴ — صفر ارتباط در اجرای برنامه و مدیریت داده‌های قدیمی

**کار:** telemetry و fallbackهای vendor، جست‌وجوی راهنما، آیکون شرکت‌ها، بررسی نسخه، validation و سرویس‌های خودکار وابسته به upstream به مسیر مستقل یا حالت غیرفعال روشن منتقل شوند. جریان لازم هر قابلیت حفظ و مستقل طراحی شود؛ خاموش‌کردن کور سرویس‌های مرکزی یا جعل نتیجهٔ اعتبارسنجی راهکار این برنامه نیست.

**کنترل چندلایه:** مقدار مؤثر تنظیمات DB/cache/env بررسی شود؛ تغییر env تنها معیار قبولی نیست. برنامه تلاش ممنوع تولید نکند و در کنار آن خروجی server/worker فقط از دروازهٔ مجاز باشد. مرورگر CSP سازگار با iframe و worker renderer داشته باشد. در اولین render هم fallback خارجی فعال نشود. قطع proxy نباید باعث اتصال مستقیم شود.

**دامنهٔ داده:** URLهای product-owned در تنظیمات، محتوای seed قدیمی، assetها و cacheها به‌صورت read-only موجودی شوند. متن مشتری، پیوست‌ها، فیلدها و سوابق به‌صورت گروهی با جست‌وجوی واژه بازنویسی نشوند. URL مشتری که به مقصد ممنوع اشاره می‌کند نباید خودکار بارگذاری شود؛ مرجع داده بدون طرح مصوب تخریب نشود. migration فقط برای فیلدهای مشخصِ متعلق به محصول، با پشتیبان و امکان برگشت تهیه شود.

**خروجی:** مرورگر، API و worker هنگام استفادهٔ عادی به Twenty درخواست ندهند؛ آیکون شرکت‌ها، timeline و lookupها بدون سرویس خارجی آن کار کنند؛ شبکهٔ زیرساخت نیز مسیر دورزدن مستقیم را ببندد.

**شما چه چیزی چک می‌کنید؟** جدول‌ها، جست‌وجو، ایجاد/ویرایش الگو، تغییر موجودیت، درج متغیر و preview کار کنند. گزارش متنی شبکه، DNS و ردشدن تماس آزمایشی عمدی ارائه شود؛ screenshot لازم نیست. تست provider فقط mock/no-send باشد.

## مرحلهٔ ۵ — نصب، image، marketplace و به‌روزرسانی مستقل

**کار:** image اختصاصی با digest ثابت، registry/رسانهٔ نصب خودتان، manifest انتشار، نسخه‌های تثبیت‌شده و updater کنترل‌شده آماده شوند. installer برای گرفتن Compose/env یا آخرین tag به upstream نرود. کاتالوگ اپ‌ها و assetهای آن از بستهٔ محلی یا registry شما تأمین شوند؛ همگام‌سازی خودکار عمومی مسیر پنهان تماس باقی نگذارد.

**ساخت:** CI و ساخت production نیز با موجودی وابستگی و منابع کنترل‌شده بررسی شوند. صرف نصب app از tarball، استقلال کل پلتفرم نیست. front، renderer، server و emails تغییرکرده باید همگی در artifact واقعی وارد شوند. برای renderer، build جاوااسکریپت و تولید declaration/alias طبق target همان نسخه کامل انجام شود؛ green شدن روی سورس یا کانتینر قدیمی پذیرفته نیست.

**خروجی:** دو پروفایل آزموده: نصب مشتری و کلاد شما؛ هر دو بدون نیاز به زیرساخت Twenty. سرویس‌های مجاز خودتان یا SMS از طریق allow-list صریح عمل کنند. «آفلاین کامل» در صورت انتخاب، نیازمند بستهٔ همهٔ وابستگی‌ها و نبود سرویس اینترنتی الزامی است.

**شما چه چیزی چک می‌کنید؟** روی ماشین تازه نصب می‌کنید، وارد می‌شوید و قابلیت‌های اصلی کار می‌کنند؛ نسخه و hash artifact با نسخهٔ سرو‌شده تطبیق دارد؛ نصب و دریافت نسخه هیچ فایل یا پاسخ لازم از Twenty نمی‌خواهد.

## مرحلهٔ ۶ — پذیرش نهایی، ارتقا و بازیابی

**پیش‌شرط:** پایان مرحله‌های ۱ تا ۵؛ نبود برند نهایی یا یک مسیر شبکهٔ حل‌نشده مانع اعلام DONE است.

| سناریو | معیار قبولی |
|---|---|
| نصب تازه | نام/لوگو/آیکون/لینک‌ها درست؛ هیچ وابستگی upstream برای نصب و startup وجود ندارد. |
| ارتقای مشتری قبلی | داده و تنظیمات مشتری حفظ شده؛ تغییرات محصول محدود و قابل بازگشت؛ نسخهٔ قدیمی مرورگر موجب تماس قدیمی نمی‌شود. |
| ورود و بازیابی | فرآیندهای auth و ایمیل با دامنه و برند همین نصب سالم‌اند. |
| جدید/ویرایش الگوی پیامک | اعتبارسنجی واضح، حفظ متن خطادار، بازگشت صحیح پس از ایجاد و ذخیره/بارگذاری مجدد سالم‌اند. |
| موجودیت و متغیرها | همهٔ منابع پشتیبانی‌شده فیلد خودشان را دارند؛ تغییر منبع، preview و relation رفتار درست قبلی را حفظ کرده‌اند. |
| lookup و timeline | آیکون‌ها بدون twenty-icons و بدون تصویر خراب کار می‌کنند. |
| لینک‌ها | هیچ href فعال متعلق به Twenty یا حساب‌های اجتماعی آن در رابط و ایمیل تولیدی نیست؛ مقصدهای خودتان کار می‌کنند. |
| شبکه | capture مرورگر/server/worker و DNS در مجموعهٔ سناریوها هیچ تماس ناخواسته نشان نمی‌دهد؛ تماس ساختگی عمدی از مسیر مستقیم هم مسدود است. |
| background jobs | cron، restart، marketplace و updater در سناریوی آزمون پوشش دارند؛ نبود ترافیک فقط در چند کلیک به معنی پوشش همهٔ jobها نیست. |

## کنترل تداخل و حفظ برنامه

- هر مرحله شاخه و commit مستقل با parent معلوم داشته باشد؛ مراحل وابسته به ترتیب ادغام شوند. commit مستندات با implementation اشتباه نشود.
- ابتدا baseline و وضعیت تغییرات محلی ثبت شود. reset/clean/force و stash خودکار روی کار درحال اجرای شما ممنوع؛ worktree جدا استفاده شود.
- rename سراسری `twenty` در نام package، env، import، شناسه‌ها، مسیر داده و schema انجام نشود. این‌ها ممکن است قرارداد فنی موجود باشند؛ هر مورد قابل‌نمایش یا مولد URL از همان مرز اصلاح شود. نام فنی داخلی و شناسهٔ پایدار مشتری بدون طرح migration تغییر نکند.
- تغییرهای برند عمومی از تغییرهای state هر workspace تفکیک شوند. لوگو و اطلاعات مشتری جایگزین خودکار نشوند.
- APIهای auth، permission و حفاظت worker حفظ شوند. برای بستن یک درخواست خارجی، نتیجهٔ موفق ساختگی تولید نشود.
- build از درخت تمیز و commit مشخص؛ آزمون بستهٔ واقعاً نصب‌شده و فایل‌های سرو‌شده. typecheck/lint و regression مرتبط پس از تغییر اجرا شوند؛ نمونه‌های جدید فقط در محدودهٔ fixture مشخص پاک‌سازی شوند.
- هدف نهایی علاوه بر حذف ظاهری، نداشتن مسیر تماس است؛ در CI، اسکن URL/asset/ترجمه/HTML ایمیل و آزمون عدم خروج ترافیک regression شوند. رشته‌های داخلی فنی جدا از URL و نام قابل‌نمایش طبقه‌بندی شوند.
- نتیجهٔ capture محدود به زمان و سناریوی ثبت‌شده است؛ هر نسخهٔ بعدی نیز باید از gate یکسان بگذرد.

## ورودی‌های لازم برای پایان مرحله‌های برند

نام فارسی و انگلیسی محصول؛ لوگوی اصلی و نسخهٔ مناسب تم‌ها؛ دامنهٔ اصلی و نشانی نصب؛ ایمیل پشتیبانی؛ مقصد راهنما و changelog؛ شبکه‌های اجتماعی خودتان یا تصمیم حذف آن‌ها؛ نام فرستنده و دامنهٔ ایمیل؛ رنگ اصلی برند.

نبود این ورودی‌ها مانع موجودی‌برداری و طراحی زیرساخت نیست؛ تا ارائهٔ مقادیر واقعی، ظاهر نهایی آمادهٔ پذیرش اعلام نشود. برنامهٔ حاضر هیچ مقدار جعلی را به‌عنوان برند یا آدرس واقعی شما فرض نکرده است.

## مرجع اجرا و نظارت

- مسئول هماهنگی، بررسی diff، پذیرش هر مرحله و پذیرش مستقل پایانی: Codex در این گفتگو.
- اجراکنندهٔ تغییرات: Cursor. شروع فقط با تسک فعال؛ بعد از گزارش نتیجه، بدون دریافت تسک بعدی محدودهٔ تازه شروع نشود.
- تسک فعال: [BI-01](../tasks/BI-01-internal-help.md).
- وضعیت و شواهد: [Brand Independence Recovery](../recovery/brand-independence.md).
- بعد از هر تسک، Code SHA و commit مستندات جدا گزارش شوند؛ PASS خوداظهاری اجراکننده تا بررسی Codex به معنی پذیرش نهایی نیست.
- پس از پایان مرحله‌های ۱ تا ۵، Codex روی artifact نهایی و شواهد قابل دسترسی بررسی مستقل مرحلهٔ ۶ را انجام می‌دهد؛ نبود دسترسی لازم، UNVERIFIED ثبت می‌شود.
- screenshot لازم نیست. نتیجه با diff، تست رفتاری، متن DOM، مسیر route، origin مقصد و شمارندهٔ درخواست شبکه اثبات شود.
